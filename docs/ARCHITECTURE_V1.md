# Архитектура — версия 1

Документ описывает backend и базу данных модуля «Признание заслуг».
Состояние на конец этапа 1: backend и БД подготовлены отдельно, фронтенд
не изменялся и продолжает работать на `localStorage`.

---

## 1. Общая картина

```
Признание заслуг.html          employees.json, Рейтинг.json
   (React SPA, localStorage)        (исходные данные)
          │                                │
          │  этап 2: переход на API        │ импорт (seed)
          ↓                                ↓
   ┌──────────────────┐            ┌──────────────────┐
   │  backend         │──── pg ───▶│  PostgreSQL      │
   │  Node + Express  │            │  12 таблиц       │
   └──────────────────┘            └──────────────────┘
```

На этом этапе связь «фронтенд → backend» намеренно не подключена.

├── src/
│   ├── config/index.js           чтение .env, значения по умолчанию
│   ├── db/pool.js                пул pg, query, withTransaction

│   ├── routes/                   маршруты

Слои не перепрыгивают друг через друга: контроллер не ходит в базу,
репозиторий не знает про HTTP.

## 3. База данных

### Таблицы

| Таблица | Назначение | Ключевые поля |
|---|---|---|
| `roles` | роли | `code`: initiator, moderator, admin, head |
| `statuses` | статусы заявки, ровно 5 | `code`, `ui_key`, `counts_in_rating` |
| `employees` | сотрудники | `tnumber` (уникальный), `fio`, `post`, `branch`, `dep`, `dept` |
| `users` | учётные записи | `login`, `password_hash`, `role_id`, `employee_id` |
| `nominations` | номинации и бейджи | `code`, `name_kz`, `name_ru`, `points` |
| `merits` | заслуги внутри номинации | `nomination_id`, `merit_kz`, `merit_ru` |
| `requests` | заявки на признание | `request_no`, `employee_id`, `status_id`, `points` |
| `request_history` | история движения заявки | `request_id`, `action`, `old_status_id`, `new_status_id` |
| `ratings` | рейтинг за год | `employee_id` + `period_year` (уникальная пара) |
| `punishments` | взыскания из ЛПО | `employee_id`, `cost` |
| `notifications` | уведомления | `user_id`, `request_id`, `is_read` |
| `attachments` | вложения | `request_id`, `history_id`, `filename` |

### Связи

```
roles ──1:N──▶ users ──N:1──▶ employees ──1:N──▶ ratings
                 │                 │
                 │                 ├──1:N──▶ requests ──N:1──▶ nominations ──1:N──▶ merits
                 │                 │              │
                 │                 │              ├──1:N──▶ request_history ──N:1──▶ statuses
                 │                 │              ├──1:N──▶ attachments
                 │                 │              └──1:N──▶ notifications
                 │                 └──1:N──▶ punishments
                 └──1:N──▶ notifications
```

Ключ работника — `employees.tnumber`, как в боевом модуле. Внутренний `id`
используется только для внешних ключей.

### Миграции

Файлы `.sql` выполняются по возрастанию имени, каждый в своей транзакции.
Выполненные записываются в `schema_migrations` — повторный запуск ничего
не дублирует. При ошибке миграция откатывается целиком.

## 4. API

Базовый префикс `/api`.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api` | список endpoints |
| GET | `/api/health` | состояние сервиса и подключения к БД |
| GET | `/api/employees` | список сотрудников; `?search=`, `?dept=`, `?limit=`, `?offset=` |
| GET | `/api/employees/:id` | сотрудник по внутреннему id или табельному номеру |
| GET | `/api/ratings` | рейтинг; `?year=`, `?limit=`, `?offset=` |
| GET | `/api/ratings/:employeeId` | рейтинг сотрудника по id или табельному номеру |
| GET | `/api/requests` | заявки; `?status=`, `?employee=` |
| GET | `/api/requests/:id` | заявка вместе с историей |
| POST | `/api/requests` | создание заявки, статус WAIT |
| PATCH | `/api/requests/:id` | смена статуса с записью в историю |

Ответ всегда содержит `ok`. Ошибка возвращается как
`{ ok: false, error: { message, status } }`.

`GET /api/health` отдаёт 200, если база доступна, и 503, если нет.

## 4a. Аутентификация и права

### Вход

`POST /api/auth/login` принимает `{ login, password }`, ищет пользователя по
логину, проверяет `is_active`, сверяет пароль через `bcrypt.compare` и
выдаёт JWT. Неверный логин и неверный пароль дают одинаковый ответ 401 —
чтобы перебором нельзя было выяснить, какие учётные записи существуют.

Ответ содержит токен и профиль. `password_hash` не покидает репозиторий:
он выбирается отдельным запросом только ради сверки.

### Токен

Подписывается `JWT_SECRET`, живёт `JWT_EXPIRES_IN` (по умолчанию 8 часов).
Полезная нагрузка:

```
{ userId, login, role, employeeId }
```

Клиент передаёт его заголовком `Authorization: Bearer <токен>`.

`JWT_SECRET` обязателен: при `NODE_ENV=production` сервер без него не
стартует, в development поднимется, но вход ответит 503. Слабое значение по
умолчанию не подставляется намеренно.

### requireAuth

`src/middleware/requireAuth.js` разбирает заголовок и проверяет подпись.
Пользователь каждый раз перечитывается из базы: роль могли поменять уже
после выдачи токена.

| Ситуация | Код |
|---|---|
| Заголовка нет | 401 |
| Формат не `Bearer <токен>` | 401 |
| Подпись неверна | 401 |
| Срок истёк | 401 |
| Пользователя нет в базе | 401 |
| `is_active = false` | 403 |
| `JWT_SECRET` не задан | 503 |

При успехе кладёт профиль в `req.user`.

### RBAC

`src/config/permissions.js` — единственный источник правды по правам,
`src/middleware/requireRole.js` — проверка. Право означает действие, а не
маршрут: у разных операций одного роутера права разные.

| Право | initiator | moderator | admin | head |
|---|:--:|:--:|:--:|:--:|
| `view` | ✓ | ✓ | ✓ | ✓ |
| `reports` | ✓ | ✓ | ✓ | ✓ |
| `create` | ✓ | ✓ | ✓ | — |
| `form` | ✓ | — | ✓ | — |
| `withdraw` | ✓ | — | ✓ | — |
| `attach` | ✓ | — | ✓ | — |
| `refsView` | — | ✓ | ✓ | — |
| `refsEdit` | — | — | ✓ | — |
| `moderate` | — | ✓ | ✓ | — |
| `state` | — | ✓ | ✓ | — |
| `remove` | — | — | ✓ | — |

`requirePermission('moderate')` отдаёт 403 и перечисляет в `details`
имеющиеся права — так проще отлаживать.

### Роль head

Руководитель получает только `view` и `reports`: смотрит справочник,
заявки и рейтинг, но ничего не меняет. Это закрывает конфликт **C-2**,
который до сих пор оставался открытым: в прототипе роль существовала, но
прав не имела ни одного, а видимость разделов давалась алиасом на
модератора с пометкой TODO.

### Защита маршрутов

| Endpoint | Доступ |
|---|---|
| `GET /api/health` | **открыт** — нужен для мониторинга |
| `POST /api/auth/login` | **открыт** |
| `GET /api/auth/me` | требует токен |
| `GET /api/employees`, `/:id` | токен + `view` |
| `GET /api/ratings`, `/:employeeId` | токен + `reports` |
| `GET /api/requests`, `/:id` | токен + `view` |
| `POST /api/requests` | токен + `create` |
| `PATCH /api/requests/:id` | токен + `moderate` |

Что не логируется ни при каких условиях: пароль, `password_hash`, токен,
`JWT_SECRET`, `DATABASE_URL`.

## 5. Бизнес-логика: что взято из проекта

Ничего не выдумано, всё перенесено из прототипа и «Описания проекта».

**Статусы** — пять, коды боевого модуля:

| code | ui_key | Название | В рейтинг |
|---|---|---|---|
| WAIT | pending | В ожидании | нет |
| DONE | sent | Исполнено | **да** |
| CANCEL | withdrawn | Отменено | нет |
| REJECTED | cancelled | Отклонено | нет |
| REJECTED_ADMIN | rejected_admin | Отклонено администратором | нет |

**Номинации** — шесть, баллы из `MR_NOM_DATA`:

| Код | KZ | RU | Баллы | Бейдж |
|---|---|---|---|---|
| NOM-101 | Кәсіпқойлық | За инновационность | 160 | KEREMET, золото |
| NOM-102 | Тиімділік | За профессионализм | 110 | TAMASHA, серебро |
| NOM-103 | Белсенділік | За эффективность | 70 | ǴAJAP, бронза |
| NOM-104 | Командалық жұмыс стилі | За командный стиль работы | 40 | JARAISYŃ, зелёный |
| NOM-105 | Жәрдемдесу | За содействие | 20 | BÁREKELDI, синий |
| NOM-106 | Корпоративтік рух | За корпоративный дух | 10 | ALǴA, жёлтый |

**Переходы статусов** — из кнопок прототипа:

```
WAIT ──▶ DONE | REJECTED | REJECTED_ADMIN | CANCEL
REJECTED ──▶ REJECTED_ADMIN
DONE, CANCEL, REJECTED_ADMIN — конечные
```

**Права** (`MR_can` прототипа) перенесены в комментарии маршрутов, но
пока не применяются — авторизации ещё нет.

**Рейтинг**: баллы берутся из `Рейтинг.json` как есть и не пересчитываются
из бейджей — так делает `MR_person`. Заявки в статусе DONE добавляют баллы
номинации сверху; взыскания вычитаются.

## 6. Команды

```bash
cd backend
npm install

cp .env.example .env        # и подставить свой DATABASE_URL

npm run db:migrate          # создать таблицы и справочники
npm run db:migrate:status   # какие миграции применены

npm run db:seed             # сотрудники
npm run db:seed:users       # учётки (bcrypt)
npm run db:seed:ratings     # рейтинг
npm run db:seed:all         # всё сразу

npm start                   # запуск
npm run dev                 # запуск с перезагрузкой
```

Перед первым запуском нужна база:

```sql
CREATE DATABASE priznanie_zaslug ENCODING 'UTF8';
```

## OPEN QUESTIONS / CONFLICTS

Расхождения между документами. Ни одно не решено самостоятельно — где
пришлось выбирать, чтобы код заработал, выбор помечен и обратим.

### C-1. Как называется роль руководителя: `manager` или `head`

1. **Первое значение** — задание этапа 1, раздел «roles»: минимальные роли
   `initiator, moderator, admin, manager`.
2. **Второе значение** — прототип `Признание заслуг.html`, массив `MR_ROLES`:
   `{ key: "head", label: "Руководитель", group: "HeadMeritRecognition" }`.
   То же в `employees.json` (`"role": "head"`) и в «Описании проекта»
   («руководитель, IsHeadMeritRecognition»).
3. **Влияние** — код роли в таблице `roles`, сопоставление при импорте
   пользователей, будущие проверки прав. При `manager` импорт учётки
   руководителя упадёт с «неизвестная роль».
4. **Что решить** — оставить `head` (как в боевом модуле) или переименовать
   в `manager`. **Сейчас взят `head`**, потому что правило этапа —
   использовать существующую логику, а не придумывать новую.

### C-2. Какие права у руководителя

1. **Первое** — `MR_can` в прототипе: роль `head` не входит ни в один
   список действий, то есть прав нет вообще.
2. **Второе** — `MR_nav`: `if (role === "head") role = "moderator";` с
   комментарием `TODO: уточнить права руководителя`.
3. **Влияние** — руководитель видит «Администрирование» и «Справочники»,
   но не может ничего сделать: кнопки скрыты. В API прав пока нет вовсе.
4. **РЕШЕНО** — руководителю оставлены только `view` и `reports`. Матрица
   реализована в `src/config/permissions.js`, конфликт закрыт.

### C-3. Код группы администратора написан двумя способами

1. **Первое** — `MR_ROLES` прототипа: `group: "AdminMeritRecognitin"`
   (пропущена буква «o»).
2. **Второе** — `employees.json` и «Описание проекта»:
   `AdminMeritRecognition`.
3. **Влияние** — сопоставление с группой доменного каталога.
4. **Что решить** — подтвердить правильное написание. **В миграции взято
   `AdminMeritRecognition`** как совпадающее в двух источниках из трёх.

### C-4. Сколько учёток и записей рейтинга

1. **Первое** — «Описание проекта.docx»: «employees.json (24 сотрудника,
   3 учётки) и Рейтинг.json (25 записей)».
2. **Второе** — фактические файлы: `employees.json` — 24 сотрудника и
   **4** учётки; `Рейтинг.json` — **22** записи.
3. **Влияние** — ожидания при проверке импорта.
4. **Что решить** — обновить описание. Расхождение объясняется: позже
   добавлена учётка руководителя, а из рейтинга убраны трое отсутствующих
   в справочнике.

### C-5. Версия React

1. **Первое** — «Описание проекта.docx»: «single-file React 18 SPA».
2. **Второе** — `README.md` и `CLAUDE.md`: React 19 (19.2.6).
3. **Влияние** — на backend не влияет, но документация противоречит себе.
4. **Что решить** — поправить описание.

### C-6. У троих бейджи не сходятся с годовым баллом

1. **Первое** — `Рейтинг.json`, поле «Балл за год» = 50 у Абильмажиновой,
   Дуйсеновой и Абдыровой.
2. **Второе** — их же счётчики бейджей дают 40 при номиналах
   160/110/70/40/20/10. Разница 10 — похоже на недостающий жёлтый бейдж.
3. **Влияние** — если считать баллы из бейджей, рейтинг у троих упадёт на
   10. В карточке «Просмотр благодарностей» бейджей на один меньше, чем
   соответствует баллам.
4. **Что решить** — исправить исходные данные или подтвердить, что
   годовой балл первичен. **Импорт берёт баллы как есть и не пересчитывает**,
   расхождение печатается в отчёте.

### C-7. Откуда берутся баллы рейтинга

1. **Первое** — `MR_person`: если запись в `Рейтинг.json` найдена, баллы
   берутся оттуда (`e.q[2]` за квартал, `e.year` за год) с явным
   комментарием «не из суммы бейджей».
2. **Второе** — если записи нет, баллы считаются из сгенерированных
   благодарностей (`MR_grantsAll`), то есть из суммы номиналов.
3. **Влияние** — два разных источника истины для одного показателя.
4. **Что решить** — какой путь останется после перехода на базу.

### C-8. Целевая СУБД

1. **Первое** — задание этапа 1: PostgreSQL.
2. **Второе** — «Описание проекта.docx», раздел о планах: «бэкенд на
   Node + SQLite».
3. **Влияние** — выбор СУБД и синтаксис миграций.
4. **Что решить** — подтвердить PostgreSQL. **Реализовано на PostgreSQL**
   по заданию этапа.

### C-9. Квартал рейтинга зашит жёстко

1. **Первое** — `MR_person`: за квартал всегда берётся `e.q[2]`, то есть
   третий.
2. **Второе** — там же фильтр благодарностей по месяцам 7–9.
3. **Влияние** — «текущий квартал» не вычисляется от даты; в другом
   квартале показатели останутся от третьего.
4. **Что решить** — вычислять квартал от даты или оставить отчётным
   периодом третий квартал.

### C-10. Полей профиля нет в исходных данных

1. **Первое** — личный кабинет прототипа показывает день рождения,
   телефоны, почту, руководителя и кабинет.
2. **Второе** — в `employees.json` и `Сотрудники.xlsx` таких колонок нет,
   поля выводятся как «—».
3. **Влияние** — `users.email` после импорта пустой, авторизация по почте
   пока невозможна.
4. **Что решить** — добавить колонки в `Сотрудники.xlsx`.

## Закрытые расхождения с ДТЗ

- **Статус «На доработке»** (`REVISION`). Модератор возвращает заявку
  инициатору с обязательным примечанием; оно хранится в `requests.revision_note`
  и показывается в карточке. Инициатор отправляет заявку заново
  (`POST /api/requests/:id/resubmit`). На доработке баллы остаются
  списанными: заявка не закрыта, и списывать второй раз было бы нечестно.
- **Запись справочников.** `GET/POST/PATCH/DELETE /api/refs/:kind` для
  номинаций, заслуг, фраз и вопрос-ответа под правами `refsView` и
  `refsEdit` — до этого права были объявлены, но применить их было негде.
  Записи не удаляются, а выключаются: на них ссылаются заявки.
- **Справочники «Фраза» и «Вопрос-Ответ»** перенесены из прототипа в базу
  (17 и 16 записей), источник — `frontend/refs.json`.
- **Журнал действий на экране**: раздел «Журнал действий» у администратора,
  фильтры по учётной записи, действию и результату.

## Закрытые инженерные дыры

- **CI**: `.github/workflows/ci.yml` — миграции, сиды и тесты на каждый
  push и pull request, плюс разбор встроенного скрипта прототипа.
- **Счётчик попыток входа** перенесён в таблицу `login_attempts`: раньше
  он жил в памяти процесса, рестарт его обнулял, а за балансировщиком лимит
  умножался на число экземпляров.
- **Отзыв токенов**: `users.tokens_valid_from` — черта, раньше которой
  выданные токены не принимаются. Двигается при выходе
  (`POST /api/auth/logout`), при отзыве администратором
  (`POST /api/auth/revoke/:id`) и при отключении учётной записи. Продление
  сессии — `POST /api/auth/refresh`.
- **Область видимости руководителя**: реестр и карточка заявки сужаются до
  его подразделения и всех вложенных (рекурсивный обход дерева). Заявку
  чужого подразделения он не откроет и по прямой ссылке.
- **Квартал рейтинга** считается от текущей даты, а не зашит третьим.
- **Справочник подразделений**: таблица `departments` строится из полей
  сотрудника (`npm run db:departments`), `employees.department_id` и
  `ratings.department_parent_id` заполнены.

## Ограничения текущего этапа

- Почта не отправляется: адресов сотрудников нет ни в `employees.json`, ни
  в базе, а почтовый сервер банка не назван. Механизм готов — как только
  появятся адреса в `users.email`/`employees.email` и `MAIL_HOST`,
  рассылка заработает без правок кода.
- Очередь писем разбирается сама раз в `MAIL_INTERVAL_MIN` минут
  (по умолчанию 5). Ручной маршрут `POST /api/notifications/flush`
  остался — чтобы разобрать очередь немедленно.
- Полный прогон тестов против облачной базы занимает около 12 минут: каждый
  запрос идёт до Ирландии. На своей PostgreSQL будет заметно быстрее.
- Дерево подразделений построено из текстовых полей сотрудника — других
  данных о структуре нет. При появлении настоящего справочника из кадровой
  системы `npm run db:departments` заменяется импортом.

- Фронтенд переведён на API в части заявок: создание и смена статуса идут
  на сервер, реестр перечитывается оттуда же. Записи, созданные до этапа 3,
  остаются локальными — их отличает отсутствие `srvId`.
- Авторизация работает: все endpoints кроме `/api/health` и
  `/api/auth/login` требуют токен, действия проверяются по матрице прав.
- Прав `form`, `refsView`, `refsEdit` пока негде применить —
  соответствующих маршрутов в API ещё нет. `withdraw` применяется на
  маршруте отзыва, `remove` — на удалении заявки, `attach` — на вложениях,
  `state` — на разборе очереди писем.
- Отзыва токенов нет: выданный токен действует до конца срока.
- `POST /api/requests` списывает баллы инициатора и отклоняет дубль (409).
  Стоимость заявки берётся из справочника номинаций, а не из тела запроса.
  Баллы возвращаются при отзыве, отклонении и удалении заявки из ожидания;
  из конечных статусов возврата нет, поэтому дважды вернуть нельзя.
- Таблицы `merits` (19 заслуг), `phrases` (17), `faq` (16),
  `departments` (21), `notifications` и `attachments` в работе.
  `punishments` пуста: исходных данных по взысканиям нет ни в Excel,
  ни в JSON — только упоминание в документах.
- `ratings.rank` заполняется скриптом `npm run db:rank` и отдаётся с
  пометкой `rank_source: stored`. Счёт на лету остался запасным путём.
  `department_parent_id` пуст: справочника подразделений нет.
